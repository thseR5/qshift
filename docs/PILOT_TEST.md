# Pilot test methodology (future; not authorized or performed)

Do not use real customer content until explicit H2 authorization and privacy/legal setup. A future pilot should start with staff-only, fictional-to-sanitized examples and a small set of opt-in firms.

1. Pre-register success measures: time from request to reviewed draft, correction rate, clarification rate, price mismatch count, approval/rejection, and user-reported trust. Do not use synthetic fixture metrics as pilot results.
2. Compare Qshift drafts with a designer's independently prepared quotation revision. Have a second reviewer verify line selection, rate provenance, quantities, tax assumptions and totals.
3. Set stop conditions before testing: any wrong approved price, cross-tenant access, unauthorized approval, accidental external send, missing audit event, or unresolved privacy/security incident stops the pilot.
4. Record explicit opt-in, model/transcript correction, human approval and deletion requests. Minimize stored content and agree a retention period.
5. Review outcomes by language and input type. Report denominators and confidence intervals; keep transcription WER separate from extraction quality.
6. Conduct a post-pilot security, legal, data-retention and platform-policy review before expansion.

No live pilot has been run. No commercialization or valuation claim is made.
